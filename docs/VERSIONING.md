# OpenYoink 版本号

正式版用 `主版本.次版本.补丁版本`。看用户升级后会遇到什么，不按 PR 数量、代码行数或开发时长定级。

| 升哪一位 | 判断方法 | 例子 |
| --- | --- | --- |
| 补丁 `1.8.15 → 1.8.16` | 原有功能恢复正常；兼容的稳定性、性能或无障碍修复 | 文件拖出后拉环不再持续高亮 |
| 次版本 `1.8.x → 1.9.0` | 用户多了一项可以使用的能力，原有数据与工作流仍可用 | 新增可选模块、增加一种文件夹操作 |
| 主版本 `1.x → 2.0.0` | 已支持的环境、数据或工作流不再兼容，用户必须做出调整 | 停止支持原先可用的 macOS 版本；移除已有功能；暂存架数据无法自动迁移 |

一个版本包含多项改动时，按影响最大的那一项定级；升主版本或次版本时，右边各位归零。内部重构本身不算新功能。只改 README、网站、CI 或测试，一般不用发布 App。准备下一个功能版时，如有影响当前稳定版的紧急问题，可从稳定版单独发补丁。

## 正式版与本机测试版

- 用户看到的版本是 `MARKETING_VERSION`。括号内的 `CURRENT_PROJECT_VERSION` 是构建号，Sparkle 用它判断能否升级。每发一次正式版，取稳定更新源中最大的整数构建号加一；跨次版本、主版本都不归零。
- 本机试用沿用上一正式版的版本号，构建号使用 `上一正式 build.本地序号`。例如 `1.8.15 (55.16)` 是测试包，随后发 `1.8.16 (56)`；同一轮再次给人试用时递增本地序号。本地编号不进公开 tag、appcast 或 Homebrew。
- 公开过的版本、tag 和安装包不可覆盖。发现问题，即使决定回退代码，也用下一个补丁号和新构建号发布。仅上传失败时，重传原来已签名的同一份 DMG。

## 发版时核对

1. 从最新 `main`、GitHub Release 和 `docs/appcast.xml` 核对上一正式版本、构建号。记录本机验收的提交，确认正式包与它之间的 App 源码差异符合预期。
2. 同步 OpenYoink 应用 target 的 Debug、Release 版本设置；用同一组版本号打包。`Scripts/make-release.sh` 在归档前检查版本和构建号是否递增。
3. 从一个 DMG 生成 Sparkle 签名和 Homebrew SHA-256。公开后回读下载文件，核对 tag、包内版本、appcast 和 cask；不要为不同渠道分别重打包。
